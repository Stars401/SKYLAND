## 执行纪律（强制 — 违反任意一条即视为未完成本技能）

1. **严格按本技能的工作流程逐步执行**，不得跳步、不得省略中间产出；流程中声明的每一步都必须有对应的实际动作或输出。
2. **产物落点**：生成的文件一律写入当前工作目录（或用户在本次请求中明确指定的位置），文件名遵循本技能的命名约定；禁止把产物写到工作区根目录之外或临时目录。
3. **数据边界**：只读取本技能流程声明需要的数据源（如 todo_read / 用户消息），禁止为"丰富内容"而虚构未发生的工作、编造数据或引用不存在的文件。
4. **冲突上报**：若用户请求与本技能流程冲突（如要求跳过数据拉取、伪造日期），先说明冲突点并征求确认，未经确认不得擅自偏离。
5. **完成汇报**：结束时必须逐项核对产出物清单，按「做了什么 → 产物在哪 → 遗留/下一步建议」三段式汇报，不得只回一句"已完成"。

# 代码审查技能

## 目标
给出可执行的、按优先级排序的代码修改建议。

## 工作流程

### 第一步：获取代码
- 用户粘贴代码 → 直接进入第二步
- 用户给文件路径 → `read_file(path="...")` 读取
- 用户给目录 → `glob(pattern="**/*.rs")` 定位后逐个 `read_file`

### 第二步：三维度审查

**🔴 正确性（必须修 — 会导致 Bug 或崩溃）**
- 逻辑错误（条件反转、边界溢出、空指针解引用）
- 并发问题（竞态条件、死锁）
- 资源泄漏（未关闭文件/连接/锁）
- 错误处理缺失（`unwrap()` / 忽略 `Err`）

**🟡 安全性（建议修 — 存在攻击面）**
- 注入（SQL/命令/路径穿越/XSS）
- 敏感信息泄漏（硬编码密钥、日志打印密码）
- 不安全的反序列化 / 不安全的随机数
- 权限检查缺失

**🟢 可读性（可选 — 提升维护性）**
- 命名不表意（变量/函数/类型名）
- 函数过长（>50 行）或嵌套过深（>3 层）
- 重复代码（可提取公共函数）
- 缺少关键注释（复杂算法的 why）

### 第三步：输出审查报告

对话中直接展示：

```markdown
## 代码审查报告

### 🔴 必须修（{n} 项）
| # | 位置 | 问题 | 修复方案 |
|---|------|------|---------|
| 1 | `file.rs:L42` | 空指针解引用 | 添加 None 检查 |

**修复示例：**
```rust
// 修复前
let val = map.get(key).unwrap();

// 修复后
let val = map.get(key).ok_or_else(|| format!("key not found: {}", key))?;
```

### 🟡 建议修（{n} 项）
...

### 🟢 可选优化（{n} 项）
...
```

### 第四步：可选生成报告文件
若用户需要正式文档：
- `create_document(path="代码审查报告_{日期}.docx", title="代码审查报告 {日期}", content=报告Markdown)` → Word
- `create_pdf(path="代码审查报告_{日期}.pdf", title="代码审查报告 {日期}", content=报告Markdown)` → PDF

## 质量标准
- 每条问题必须有：文件:行号 + 问题描述 + 修复代码示例
- 只评论给出的代码，不臆测未提供的上下文
- 严重度排序不可随意 — 正确性 > 安全 > 可读性

## 失败处理与红线
- 
ead_file 报错（文件过大/路径无效/编码问题）→ 原样告知错误，请用户直接粘贴代码，不要凭空推测文件内容
- glob 返回空 → 告知用户未找到匹配文件，建议检查路径或改用粘贴
- **红线**：只评论给出的代码，不臆测未提供的上下文；每条问题必须有位置+描述+修复代码
